# 2026-09-13 — G7 frena el auto-etiquetado si no puede revisar datos protegidos

## Qué se hizo

- `auto-etiquetar.yml` pide a `CosteAR-admin` el veredicto G7 con el repositorio, el PR y el SHA
  exacto antes de ejecutar G1–G6 para cualquier PR contra `dev`.
- El consumidor espera hasta cinco minutos el status `G7/datos-de-cliente`. Sólo `success` deja
  continuar; PAT ausente, dispatch fallido, timeout y `failure` conservan la puerta cerrada.
- Se agregó permiso de lectura de commit statuses. La lista privada y los términos inspeccionados
  no se leen ni se imprimen en este repositorio público.

## Decisiones que tomé sobre la marcha

- **Qué decidí:** aplicar G7 sólo cuando la base es `dev`.
  **Qué otra opción había:** frenar también las promociones contra `staging`.
  **Por qué elegí esta:** el contrato de `CosteAR-admin` acepta exclusivamente PRs con base `dev`;
  aplicarlo a promociones las bloquearía siempre y rompería G4.
- **Qué decidí:** pedir G7 antes del corte por PR draft.
  **Qué otra opción había:** saltear drafts y pedir el veredicto recién al marcar el PR listo.
  **Por qué elegí esta:** el issue dice que el dispatch ocurre al arrancar y así el status queda
  preparado para el mismo SHA antes de que el PR pueda etiquetarse.
- **Qué decidí:** después de un dispatch fallido, seguir sondeando hasta el límite.
  **Qué otra opción había:** cortar de inmediato.
  **Por qué elegí esta:** el contrato define la ausencia de status como resultado y exige esperar
  hasta cinco minutos; además evita confundir una respuesta demorada con una ausencia definitiva.
- **Qué decidí:** consultar el status más recientemente actualizado del contexto exacto.
  **Qué otra opción había:** usar el estado combinado del commit o el primer status devuelto.
  **Por qué elegí esta:** puede haber varios veredictos para el mismo SHA durante las pruebas;
  sólo el más nuevo representa la decisión vigente y otros contextos no pertenecen a G7.
- **Qué decidí:** no copiar el token de la sesión ni modificar secretos para completar la prueba.
  **Qué otra opción había:** crear un secreto de repositorio con credenciales personales.
  **Por qué elegí esta:** habría ampliado permisos, ocultado el defecto de configuración y tratado
  una credencial como dato de prueba.

## Dónde el issue no alcanzaba

- No decía que `statuses: read` debía agregarse. Sin ese permiso, el `GITHUB_TOKEN` no puede leer
  la respuesta aun cuando admin la publique.
- No especificaba si los drafts debían disparar G7 ni el intervalo de sondeo. Se eligieron treinta
  lecturas con diez segundos entre ellas, que cubren cinco minutos sin hacer espera ocupada.
- Afirmaba que `CIRCUITO_PAT` ya estaba disponible desde `admin#89`, pero la corrida real
  `34783699829` lo recibió vacío. El listado de secretos del repo también está vacío y esta cuenta
  no tiene permiso para inspeccionar la visibilidad de secretos de organización (HTTP 403).
- Un PR que modifica `auto-etiquetar.yml` no puede demostrar el auto-etiquetado final sobre sí
  mismo: la guarda existente impide que un workflow se apruebe solo. Se verificó que `success`
  permite continuar hasta el corte por draft, sin presentar eso como una corrida originada en admin.

## Qué quedó afuera

- La corrida cross-repo real con `success` emitido por `CosteAR-admin` y el auto-etiquetado de un
  PR normal. Está bloqueada porque Actions no recibe `CIRCUITO_PAT`; se abrió frontend #173.
- No se tocó la configuración de secretos, `auto-merge.yml`, G1–G6, `src/` ni los tests.
- No desapareció ni cambió de título ningún test.
